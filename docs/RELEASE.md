# Порядок безопасной проверки и публикации Fabrica Coffee Admin Demo

## 1. Область действия
Этот регламент относится только к `fabrica-coffee-admin-demo`.
Демо не связано с реальным сайтом Tilda: изменения меню сохраняются только в localStorage браузера.
Здесь не размещаются API-ключи, персональные данные, реальные заказы или коммерческие секреты.

## 2. Разработка
1. Создавать ветку вида `feature/...` или `ci/...` из свежего `main`.
2. Открывать черновой Pull Request в `main`.
3. Проверять, что изменены только ожидаемые файлы, нет случайных секретов и тесты GitHub Actions проходят.
4. Проверять новые функции руками на отдельной тестовой странице/локально. Текущий CI **не запускает браузерные e2e-тесты**.

## 3. Контроль перед объединением
- CI `Verify Fabrica Coffee demo (no deploy)` имеет состояние **success**.
- Подтверждено, что прайс и филиалы не изменились случайно.
- Предупреждение о том, что это только демо, сохранено.
- Если будут изменены данные seed, сначала проверить их по действующему меню Tilda и обновить ожидаемые числа теста обоснованно.
- Перед изменениями в браузере экспортировать резервную копию данных через имеющийся интерфейс демо.
- Владелец одобрил конкретную версию и разрешил публикацию.

## 4. Публикация
- Этот workflow **ничего не публикует**; у токена есть только `contents: read`.
- Проверить в настройках GitHub `Settings → Pages`, от какой ветки/папки сейчас публикуется сайт. Текущая конфигурация Pages через API здесь не подтверждена.
- Объединять Pull Request в `main` только после успешной проверки и явного разрешения.
- Если Pages настроен публиковать `main`, объединение изменений в эту ветку может автоматически обновить публичное демо.
- После публикации проверить URL, мобильную вёрстку и основные сценарии (филиал, поиск, цена, скрытие, экспорт/импорт). Не принимать нулевые счётчики при простом HTTP-извлечении за доказательство отсутствия каталога.

## 5. Откат
При ошибке не переписывать `main` и не выполнять force-push.
Создать отдельный Pull Request с обратным коммитом (revert), проверить CI и только затем объединять его по подтверждению владельца.
Данные localStorage в браузере пользователей откатом кода автоматически не восстанавливаются.

## 6. Отдельные сервисы Render
`jarvis-alice-voice` и `jarvis-crypto-analyst` подключены к Render и автоматически публикуются после новых коммитов `main`.
Этот документ не изменяет их настройки. Для них нужен отдельный этап: обязательные проверки PR, ограничение прямых изменений `main` и контролируемое включение deploy.
Нельзя считать наличие CI гарантом блокировки публикации: ограничения ветки GitHub и настройки Render требуют отдельной проверки.
